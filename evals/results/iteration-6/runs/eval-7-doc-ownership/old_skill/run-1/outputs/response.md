`apex-governance` owns the documentation obligation; `writing-plans` owns the plan content.

Because this is an approved cross-service API design and the work now needs a durable plan, governance should record `design_gate=satisfied`, select the durable-plan mechanism, and list the documentation sources of truth that implementation must keep aligned. It decides whether the accepted API spec/design, integration docs, matrix, or tradeoff record must be updated; the planning leaf cannot create those obligations. It also resolves the plan location in this order: repository convention, active governance or accepted-spec convention, then the neutral `docs/plans/YYYY-MM-DD-<feature-name>.md` fallback. The plan remains a plan—not a replacement spec, design record, matrix, tradeoff log, or handoff document.

Once selected, `writing-plans` turns the approved design into an execution-ready sequence. It owns the plan's exact file map, task boundaries, cross-service interfaces and dependencies, constraints copied from the approved source, acceptance criteria, exact verification commands and expected outcomes, and any governance-authorized commit boundaries. With governance active, it uses `apex-governance/references/plan_template.md` as the canonical shape and links to the approved spec/design and any required matrix or tradeoff entry rather than duplicating them.

So the handoff is: governance says **which documents must exist or stay aligned and where the durable plan belongs**; `writing-plans` says **how the approved API design will be implemented and verified task by task**. No brainstorming is needed unless a material design question is actually unresolved, and no project files should be edited in this routing-only scenario.
