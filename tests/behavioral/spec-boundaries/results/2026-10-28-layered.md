# Layered specifications: revised candidate — 2026-10-28

## Result

The five existing cases met the reviewed layering, completeness, and anti-fragmentation criteria. The important change was in the internal-algorithm case: the [baseline](2026-10-28.md) put all 32 requirements in one project specification; the revised execution used an overall specification plus focused feature and query specifications, without inventing separate releases, approvals, or lifecycles. These are observations from one fresh execution per case, not a guarantee of future behavior or a causal estimate. Executors received the same tasks and raw requirements as the baseline, only skill-creator and revised candidate rule copies, and no expected layout, suspected failure, prior results, or reviewer criteria. Software and algorithm each received their second accepted input after initial output capture. All seven captured stages preserved the supplied inputs byte-for-byte.

## Candidate and scope

The change replaces the independent-contract gate with information ownership and useful technical layers. The overall specification owns scope/shared constraints/relationships; technical specifications own definitions and acceptance detail. Simple details remain sections, and layering cannot omit semantics or duplicate their authoritative definitions. Existing consolidation wording now preserves useful layers instead of collapsing them by contract count.

The normative contract meaning of spec is unchanged. APEX, templates, working-document lifecycle rules, recovery protection, and retained-predecessor rules were not modified. No router, new workflow stage, status field, approval mechanism, or validation rule was introduced. README was synchronized. The test helper gained a snapshot command so comparisons retain actual outputs without task-specific capture scripts.

## Limits and separate checks

Review inspected actual semantics and ownership, not exact headings, preferred phrases, document counts, or reduced length. No experiment diary, per-stage plan, new per-layer approval procedure, or loss of supplied contract detail was observed in these cases. Some brief summaries still repeat technical identifiers/parameters in an overview; the run does not establish the absence of all redundant prose.

The software executor changed the versioned API path while repairing all references; exact path stability was not demonstrated. That execution choice was not required by the patch, whose existing path policy is unchanged. No new exception or corrective rule was added for that variation.

This finite evaluation does not establish long-context reliability, lifecycle correctness in every scenario, numeric conformance over all possible inputs, or real model/hardware performance. Cancellation, handoff and predecessor-retention cases were not rerun; their governing rules remain unchanged. The retained incomplete plans support only the unfinished-work boundary exercised here. Official package validation, source/link checks, and snapshot/input integrity checks are structural evidence, separate from the behavioral review. Installed skill copies were not changed. Reusable fixtures and output snapshots are retained; this run's disposable workspace is cleaned after review.
