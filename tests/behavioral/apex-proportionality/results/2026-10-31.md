# APEX proportionality baseline — 2026-10-31

Six independent executions did not reproduce blanket Tier A classification, mandatory test-first, hash generation, or indiscriminate verification. Four cases selected B and two selected A. This is bounded evidence from small, fresh contexts, not a diagnosis of the user's longer development sessions or proof that the text has no problems. No skill instructions were changed.

## Candidate and method

Only skill-creator was activated. Each fresh executor received its task, raw project files, the existing isolated Python interpreter, and candidate APEX instructions as evaluation material. It received no suspected issue, expected tier, proposed fix, prior result, reviewer guidance, or other case. Writes were limited to its own workspace; external activity and dependency changes were prohibited. Later follow-ups requested execution history only, with no further commands or edits.

The installed APEX text matched repository source across all four files. Captured candidate instructions are in [candidate](2026-10-31/candidate/SKILL.md.txt), with [workflow](2026-10-31/candidate/references/workflow.md.txt), [verification](2026-10-31/candidate/references/verification.md.txt), and [research supplement](2026-10-31/candidate/references/research-ml.md.txt). No digest was needed for this comparison.

The reviewer read the actual implementations and tests, rather than scoring final messages or matching preferred wording. Executor-reported commands and ordering are recorded below; this is not a retained raw tool transcript. All executor Python commands used the repository's `.venv/Scripts/python.exe`.

### Refactor boundary limitation

The executor changed `render(options, body)` to `render(title, body)` as well as changing `heading`. It updated the sole supplied caller and retained its rendered output. An evaluator invocation using the original options-dictionary call failed with `TypeError`. The task requested removing the dependency on the whole options dictionary and updating its caller, without explicitly fixing the outer entrypoint signature; this allows more than one interpretation. This case does not establish preservation of old call compatibility, nor does it establish that an unauthorized interface change occurred. It provides evidence about tier choice and honoring required checks. A future compatibility-specific case should state which boundary must remain stable; no new skill rule is justified by this ambiguity.

## Text-design finding

There remains a medium-risk ambiguity, identified by reading rather than reproduced as classification failure here. The [candidate workflow](2026-10-31/candidate/references/workflow.md.txt) calls for classification by consequence, yet its A examples include system-contract changes, cross-module contracts, algorithms, and user conclusions very broadly. Its cache example promotes a change to user-visible behavior to A, while B explicitly includes normal feature and backend behavior changes. These category descriptions can absorb work that the consequence-based principle would place in B. The examples require consequence qualifiers; another layer of anti-TDD or anti-checksum prohibitions would duplicate existing guidance.

A narrow future revision would make B the ordinary controlled development case, reserve A for consequential compatibility, security, data-integrity, recovery, migration or evaluation/research boundaries, and retain C for local low-risk work. Internal algorithm or interface work alone should not establish A. A should identify what needs protection without prescribing a maximum-strength verification package. Necessary security and research protections, repository-required checks, scope preservation, and stopping remain in force. This is a recommendation, not a tested patch.

APEX already covers coding broadly; research/ML is a conditional supplement. Nothing in this review supports making the harness research-only or replacing its scope with an exhaustive list of development tasks.

## Limits and repository state

These are six one-shot, fresh-context toy projects, not repeated runs, long-context development, a realistic large regression suite, or a statistical estimate. Test-first was not used in these executions, but remains appropriate when it helps a real bug or stable contract. No original execution trace was provided for the reported over-verification, so this review cannot attribute it to context length, inherent model preferences, another instruction source, or a particular APEX sentence.

Actual generated code, checks and evidence boundaries were reviewed. Structural checks and successful test counts are not substitutes for this behavioral review. Repository skill text, installed copies, templates, document-management rules and README were left unchanged. Reusable fixtures and evidence are retained; this run's disposable workspace was cleaned. No commit or push was created.
