# New-project specification evaluation — 2026-10-28

## Finding

One medium-risk design mismatch with the requested development workflow: **the current split criterion gives too little room to layered technical specifications within one product contract**. The internal-algorithm execution kept input/state rules, feature mathematics, search, persistence, and acceptance together in one project specification because they had no separately maintained contract. This reproduces the concentration tendency. It does **not** reproduce omitted technical content: all 32 supplied requirements remained substantively present, with meaningful sections.

This is not evidence that a single-file specification is always wrong, nor that the generated Mosaic document is unusable. It shows where the current rule and the user's requested project/technical-document layers diverge. The current [boundary rule](../../../../skills/managing-project-docs/references/specifications.md) permits an internal algorithm's own specification only when it is maintained as its own contract; the [topology rule](../../../../skills/managing-project-docs/references/topology.md) otherwise puts it in an owning specification's section. The observed choice follows that direction. No wording ablation was run, so this does not establish which sentence caused the choice.

## Suggested direction, not implemented

Keep one authoritative owner for each piece of information, while allowing one product contract to be expressed through an overall specification and subordinate technical specifications. The overall level owns shared constraints and relationships; important subsystem/algorithm details can have a maintained technical owner without acquiring a separate release, approval process, or independent lifecycle. Use complexity and actual implementation/verification/maintenance needs to decide where a separate document helps; do not create one per code module by default.

Such a correction should replace the restrictive boundary wording, not add a new document workflow. Preserve the accepted-contract meaning of spec, optional-plan lifecycle, input/evidence ownership, and protections against duplicated contracts and experiment logs. Neither skill, its templates, nor installed copies were modified in this run.

## Limits

These are finite, short-context synthetic cases, with explicit accepted requirements. Four cases asked for document preparation; only one involved implementation. No test here establishes long-session robustness, failure frequency, or a causal effect of context length/model behavior. There is no evidence from this run that technical semantics were systematically shortened away. Official skill/package validation passed separately; that structural result is not behavioral evidence. Reusable fixtures and selected document outputs remain under this test directory; disposable execution workspaces are removed after review.
