# Relay Audit Format v1 规范

本文件拥有审计事件、导出格式 v1 和审计消费者的验收要求（R23–R30）。

## 事件与数据约束

- **R23：** 已提交的创建、开始、取消请求和终态转换必须各有审计事件。失败事务不得产生看似已提交的事件。
- **R24：** 事件字段为 `event_id`、`tenant_id`、`job_id`、`kind`、`occurred_at`、`tenant_sequence`、`actor_type`、`actor_id`。`occurred_at` 为 UTC RFC3339；`kind` 属于已声明枚举。枚举的具体字面值尚待确定，不能由消费者猜测。
- **R25：** `tenant_sequence` 在各 tenant 内严格递增，允许空洞，不允许重复或倒序；不同 tenant 的 sequence 不可比较。
- **R28：** 只允许声明的审计字段。不得包含 `payload`、`lease_token`、`Idempotency-Key`、credentials 或原始错误堆栈。

## 导出

- **R26：** `format_version=1`。导出为 UTF-8 JSON Lines，每行一个完整事件，以换行结束；JSON 数组不是等价输出。
- **R27：** 从指定 `tenant_sequence` 之后导出，起点为 exclusive。每批最多 1000 条，返回 `next_sequence`。重复请求可以重放相同历史事件，`event_id` 不改变。
- **R29：** 审计消费者不得读取其他 tenant 的事件。不得为修复顺序而全租户混合排序后暴露数据。

## 格式验收

**R30：** 使用 golden 文件检查格式，API 状态测试不能代替格式验收。

| 要求 | 验收情境与结果 |
|---|---|
| R23–R24 | 已提交的四类变化有完整字段事件；失败事务不产生假提交事件；时间为 UTC RFC3339；kind 属于最终声明的枚举。 |
| R25 | 同 tenant 序号严格递增，包括多个事件时间相同时；允许序号空洞，不允许重复或倒序；不跨 tenant 比较序号。 |
| R26、R30 | Unicode 的 UTF-8 字节、逐行完整 JSON、末尾换行、format v1；拒绝以 JSON 数组代替；覆盖空批次及同时间事件的 golden 样例。 |
| R27、R30 | exclusive 起点、1000 条上限、分页边界、next_sequence；重放历史事件保持 event_id。 |
| R28–R30 | golden 检查敏感字段和未声明字段不出现；跨租户读取不可见其他 tenant 数据，包括多页导出。 |

版本和分页元数据的承载位置、空批次 next_sequence 等尚未决定，须在生成权威 golden 文件前补齐。
