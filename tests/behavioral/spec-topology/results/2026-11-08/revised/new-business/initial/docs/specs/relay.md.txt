# Relay 产品规范

本规范及下属规范承接项目所有者已接受的 R01–R36，维护 Relay 当前要求。契约已接受不表示实现已经完成；实现和验收进度由工作计划维护。

## 范围与契约边界

Relay 提供多租户任务创建、执行协调与审计导出。目前接受的接口版本如下，各详细规范拥有相应接口的行为和验收标准：

| 接口 | 消费方与版本 | 详细契约 |
|---|---|---|
| 公共任务 API | 移动端、合作方 SDK；API v1 | [任务 API](task-api.md) |
| Worker 插件协议 | 两个不隶属服务器团队的 worker 提供方；protocol v1 | [Worker 协议](worker-protocol.md) |
| 审计导出 | 独立更新周期的审计消费者；format v1 | [审计格式](audit-format.md) |

API 消费方按公共 API 版本发布，worker 协议兼容性单独验收，审计消费者的更新不依赖 API 发布。这三层分别维护自身定义，不能用一个接口的验收代替另一个接口的验收。

## 跨边界约束

- **R31：提交与审计。** 当状态已向调用方显示提交时，对应审计事件必须可恢复。具体事务或 outbox 方案尚未决定，任何方案都不得静默丢失审计。
- **R32：一致性。** API 层不能把 expired lease 当成功结果；worker 层不能绕过 tenant 隔离；审计事件必须对应同一次已提交状态转换。
- **R33：持久性。** 服务重启后，任务、幂等窗口及审计顺序仍须保留。这些承诺不得依赖进程内状态。
- **R34：技术边界。** Worker 内部算法和部署拓扑不是当前公开契约。HTTP 框架、数据库、队列及部署方式尚未选择；本规范不指定其产品依赖。
- **R35：排除范围。** 本轮不含计费、管理 GUI 或跨地域复制。
- **R36：交付验收。** 开发分数次会话进行。API 消费方、外部 worker 提供方和审计消费者分别验收各自接口，随后验收跨边界一致性。

## 跨边界验收

| 要求 | 必须建立的观察结果 |
|---|---|
| R31 | 状态已被调用方观察为提交后，即使发生故障并恢复，对应审计事件仍可恢复；失败事务不产生看似已提交的事件。 |
| R32 | 覆盖旧 lease 迟到结果、新 attempt、终态竞争与租户隔离，确认 API 状态、worker 确认和审计所述转换一致。 |
| R33 | 创建任务及幂等记录、推进执行并生成审计后重启服务；任务与幂等重放仍正确，租户审计顺序保持有效。 |
| R34–R35 | 实现设计不将未选择的基础设施或排除的产品能力冒充为已接受要求。 |
| R36 | 保留三类接口各自验收结果及跨边界验收结果；文档审阅、静态检查或单接口通过不能代替实际符合性证据。 |
