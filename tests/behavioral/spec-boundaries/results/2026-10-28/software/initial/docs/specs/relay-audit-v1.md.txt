# Relay 审计导出格式 v1

本文件维护已接受的 audit format v1 契约。审计消费者按此格式导入，其发布和验收不依赖公共 API 发布周期。R23–R30 的行为已接受；尚未明确的枚举字面值和导出元数据承载方式仍需细化。

## 事件与顺序

- **R23**：已提交的创建、开始、取消请求和终态转换必须各有审计事件。失败事务不得产生看似已经提交的事件。
- **R24**：事件字段为 event_id、tenant_id、job_id、kind、occurred_at、tenant_sequence、actor_type、actor_id。occurred_at 为 UTC RFC3339；kind 属于已声明枚举。
- **R25**：tenant_sequence 在各 tenant 内严格递增，允许空洞，不允许重复或倒序。不同 tenant 的 sequence 不可比较。

## 编码与分页

- **R26**：format_version=1。导出采用 UTF-8 JSON Lines，每行一个完整事件并以换行结束。JSON 数组不是等价输出。
- **R27**：从请求指定的 tenant_sequence 之后导出，边界为 exclusive；每批最多 1000 条，并返回 next_sequence。重复请求可以重放相同历史事件，event_id 不改变。

## 数据边界

- **R28**：仅允许声明的审计字段。审计中禁止包含 payload、lease_token、Idempotency-Key、credentials 或原始错误堆栈。
- **R29**：审计消费者不得读取其他 tenant 的事件；不得通过全租户混合排序后暴露数据来修复顺序问题。

## 格式验收

**R30**：使用 golden 文件验收 Unicode、空批次、多个同时间事件、分页边界和敏感字段检查；API 状态测试不能替代格式验收。覆盖 R23–R29，检查实际 UTF-8 字节、逐行完整 JSON 和末尾换行、版本、字段白名单、tenant 内顺序、exclusive 边界、1000 条上限、next_sequence 和重复导出的 event_id 稳定性，以及失败事务不出现已提交事件。

golden 文件必须遵循经接受的枚举和元数据绑定；在这些细节未决时，不能用任意示例悄然确立格式。本文不声称已有 golden 文件或验收结果。
