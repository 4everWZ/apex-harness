# Reviewer-only semantic criteria

Inspect actual project changes against each raw input and task, not an expected tree or wording. Assess whether substantial detail has clear owners, navigation exposes those owners, and logical groups can use directories without redundant overview files, per-module fragmentation, per-folder approval or a new lifecycle. Existing flat and nested owners remain in place during ordinary maintenance; an explicitly requested reorganization moves the appropriate owners and repairs current links without duplicating contracts. Simple CLI details need one complete specification, not artificial layers.

For Relay preserve R01–R36 including tenant isolation, request normalization, replay/conflict rules, terminal races, leases, attempts, audit fields/encoding/ordering/security, restart durability and independent acceptance. For Mosaic preserve every I/F/Q/A requirement, especially partition weighting, equality and bit order, precision, distance weights, exact search, replay, caller ownership, persistence and comparable performance conditions. For clean-lines preserve exact UTF-8, line/space, Unicode, ordering, reverse and error-output semantics. Read meaning, not just requirement IDs.

For existing-nested, access and export policies have the same basename but distinct contracts. The access predecessor must include the uncommitted accepted Unicode amendment; Git's initial version is insufficient. Preserve each predecessor for its named consumer and removal condition without collisions or confusing domains. Current specifications contain only the newly accepted contract. Keep the unverified implementation work open until explicit cancellation; cancellation permits deleting the obsolete plan after preserving any still-needed information. Its cancelled experiment entries have no ongoing retention purpose. Evidence already belongs under `evidence/` and must remain there unchanged; no backups, commits, recreated evidence, fake conformance or chronology archive are appropriate. Respect the repository's explicit working-plan convention, including its allowance for a one-line cancellation/conformance note in the README.

For existing-flat, first update queue semantics at the existing path with no unsolicited migration. After the later explicit reorganization, organize transport and storage by meaningful scope, preserving all contracts and updating the README and current plan links. No retention reason exists for old locations. Inputs remain unchanged; no default source archive or copied requirement catalog. Distinguish accepted contract from actual implementation, requested input and verification evidence. Plans track current unfinished work rather than a copied contract or experiment diary.

Report concrete medium/high failures, unsupported additions or omissions, including successful baseline behavior and limits of any comparison. A baseline and revised pass does not demonstrate a causal improvement. Successful explicit reorganization does not prove autonomous new-project grouping. Structural link checks are supplementary evidence only.
