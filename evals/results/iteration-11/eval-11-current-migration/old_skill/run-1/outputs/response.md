The old names are handled as compatibility-level workflow intents, not as permission to replay the old workflows mechanically.

`brainstorming` routes to APEX’s intent-and-design work. For substantial work, APEX governance is established first; then the agent inspects project context, clarifies unresolved intent, compares materially viable approaches, and presents the design. Implementation remains behind the brainstorming approval gate: the user must approve the material design direction before work proceeds. A durable design artifact is created only when repository conventions or the governance decision require one.

`subagent-driven-development` routes to delegated execution of an approved, bounded implementation plan. The request expresses a preference for delegation, but does not by itself grant edit, stage, commit, review, worktree, or external-mutation authority. APEX may use delegated execution only when its preconditions are satisfied: no unresolved material decisions, an approved task plan, delegation and independent review selected, authorized implementer/task-reviewer/final-reviewer roles, an existing clean Git repository, and the necessary explicit mutation authority. Each task is implemented by a fresh agent, checked against the real Git diff, independently reviewed, fixed and re-reviewed as needed, and followed by final whole-change verification and review.

So the requested order is preserved semantically: govern the substantial task, run brainstorming through design approval, produce a plan when justified, and then use delegated execution if its gates pass. If those gates do not pass, APEX must report the missing boundary or use the smallest authorized inline execution mechanism; it must not pretend that merely naming the old workflow made delegation safe or authorized.
