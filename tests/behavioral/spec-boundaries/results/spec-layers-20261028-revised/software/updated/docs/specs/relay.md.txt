# Relay 总体规格

本规格及其下属接口规格承接项目所有者已接受的 R01–R36 及后续已接受的 API v2 变更，是后续维护的当前契约。`tmp/product-srs.md` 和 `tmp/accepted-api-change.md` 均是保留不变的传入材料；发生差异时，当前 API 语义由下属 API 规格维护。契约接受不代表已有实现或符合性证据。

## 范围与契约归属

Relay 提供按 tenant 隔离的任务服务，由公共任务 API、外部 worker 插件协议和审计导出组成。

| 契约与当前版本 | 详细定义与独立验收的维护位置 | 原需求 |
|---|---|---|
| 公共任务 API v2 | [任务 API](relay-api.md)；供移动端和合作方 SDK 随 API 版本使用 | R01–R12（含已接受变更） |
| Worker protocol v1 | [Worker 协议](relay-worker-protocol-v1.md)；供不隶属服务器团队的两个 worker 提供方使用，兼容性独立验收 | R13–R22 |
| Audit format v1 | [审计导出](relay-audit-format-v1.md)；供独立于 API 发布周期的审计消费者使用 | R23–R30 |
| 共同一致性、持久性和范围 | 本文 | R31–R36 |

三个接口服务于同一任务产品，但分别维护版本和验收边界。修改一层时须检查其他消费者是否受影响，不能以 API 通过验收代替协议或格式验收。

API v2 不改变 worker protocol v1 的 lease、重试或结果提交语义，也不改变 audit format v1 的字段与 tenant_sequence 顺序。Worker 提供方无需仅因 API 发布重做协议验收；首次协议符合性验收仍按原契约要求执行。跨边界一致性要求继续适用。

## 共同不变量

- **R31：提交与审计可恢复性。** 状态向调用方显示为已提交时，对应审计事件必须可恢复。事务或 outbox 的具体实现未决定；任何会静默丢失已提交转换审计的方案均不符合要求。
- **R32：跨边界一致性。** API 层不得把已过期 lease 当作成功结果；worker 层不得绕过 tenant 隔离；审计必须对应同一次已提交状态转换。并发转换的胜负必须在这些观察面上保持一致。
- **R33：重启后持久性。** 服务重启后保留任务、幂等窗口和各 tenant 的审计顺序。这些承诺不得依赖仅存在于进程内的状态。

## 范围约束

- **R34：** Worker 内部算法和部署拓扑不属于当前公开契约。HTTP 框架、数据库、队列和部署方式均未选定，不将任何消息中间件或数据库产品写成既定依赖。
- **R35：** 本轮不含计费、管理 GUI、跨地域复制。
- **R36：** 开发跨多次会话；API 消费方、worker 提供方、审计消费方分别验收自身接口，再做跨边界一致性验收。

## 跨边界验收

以下是待实现后执行的验收要求，不是现有测试结果。

1. 组合取消、成功、lease 过期和重新领取的并发场景，核对 API 可见状态、worker 确认和审计事件是否对应同一提交结果；过期或迟到结果不得覆盖新 attempt 或既有终态。（R32）
2. 在提交和审计持久化相关故障边界验证恢复：凡已向调用方显示提交的转换，其审计必须可恢复；失败事务不得表现为已提交事件。（R31、R32）
3. 重启服务，验证任务、仍有效的幂等窗口及 tenant 内审计顺序继续成立；覆盖重放、领取恢复和后续导出。（R33）
4. 联合检查 API、worker、审计路径的 tenant 隔离，确保跨边界访问不会泄露任务或事件。（R32）
5. 三个接口各自通过其规格中的验收后，再确认上述组合条件。尚未执行的检查不能记为符合。（R36）
