I would work test-first. This is a deterministic behavior change with a stable public contract, so a failing automated test can credibly define the rule before implementation. The public-contract aspect makes the change Tier A even if the code edit is local: success means the agreed input produces the exact agreed output, invalid or boundary inputs retain their specified behavior, repeated evaluation is deterministic, and existing parser behavior remains compatible. If any input, output, precedence, or error semantics are not already specified by repository truth, I would resolve that contract before writing the test rather than inventing it.

Verification sequence:

1. Inspect the existing public entry point, contract documentation, rule ordering or precedence, and focused unit-test conventions. Identify representative positive, negative, boundary, ambiguity, and error cases without guessing semantics.
2. Add the smallest focused contract test for one new behavior, exercising the real public parser API and asserting the exact public result rather than implementation details or mock behavior.
3. Run that test alone and observe RED. Confirm it fails as an assertion for the missing rule, with the expected mismatch—not because of a typo, fixture problem, import error, or unrelated failure. If it passes immediately, revise the test because it does not demonstrate the new behavior.
4. Implement only enough of the parser rule to satisfy that test, preserving existing module and rule boundaries.
5. Re-run the focused test and observe GREEN. Then add the next contract or edge case through another red-green cycle, including rule-precedence interactions, malformed input, and exact error/output behavior where those are part of the public contract. Include a repeatability assertion or repeated invocation where determinism could otherwise regress.
6. Refactor only after green, then rerun the focused tests to ensure behavior remains unchanged.
7. Run the complete parser unit-test suite to catch regressions, followed by the repository's relevant type, lint, build, and public-entry-point integration checks when they can affect this contract. Existing focused tests are the preferred harness; add a separate harness only if they cannot directly observe the public boundary.
8. Review the final diff against every success criterion and synchronize any existing public API or parser-contract documentation. Record fresh command results and the final code state; claim completion only if the targeted tests, regression suite, relevant checks, implementation, and documentation agree. Report any check that could not be run as an explicit verification gap.
