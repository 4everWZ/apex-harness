## Method and baseline

Seven fresh-context executors performed 23 task stages: six continuous baseline stages, twelve revised new/existing-project stages, two revised lifecycle stages and three focused revised cases. Only skill-creator was activated. Repository documentation rules/resources were copied candidate material; actors received only their current raw task and project, not expected outcomes, reviewer criteria, previous conclusions, other projects or future tasks. Each stage was captured before supplying later material. Issue/CI data in the existing-project fixture are explicitly local mirrors; no external service was accessed.

One additional fresh-context reviewer independently read candidates, root README, raw tasks and preserved artifacts. It did not run implementations or inspect the live projects. The [case index](../README.md) and [review criteria](../review.md) define the reusable setup and evaluation. Candidate-baseline and candidate-revised resources are preserved under `2026-11-08/`; actual project captures retain relative paths with `.txt` suffixes, omitting fixture Git directories, caches and transcripts.

The baseline completed all six stages successfully. It used a [stable specification with acceptance/feedback sections](2026-11-08/baseline/loop/06/docs/specs/config-limit.md.txt), correctly distinguished feedback types, retired the bounded fix plan, retained unanswered feedback and later completed the accepted extension. Its final current state repeats some completion information across implementation text, acceptance and feedback tables. This is not a reproduced hard whitelist failure, nor a reason to fail the baseline for lacking a separate acceptance file. The revision makes the responsibility explicit and provides a default form; the comparison does not establish a causal improvement in execution correctness.
