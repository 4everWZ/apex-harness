# Relay 开发计划

## 目标与当前状态

跨会话实现并验收[Relay 当前契约](../specs/relay.md)：三个接口分别验收后，再完成跨边界一致性验收。本计划维护未完成工作、阻塞项和证据状态；规范性行为由规格维护。

项目尚无应用实现，未执行测试、实验或部署；没有实现符合性证据。当前已完成接受要求的维护归属与验收范围整理。`tmp/product-srs.md` 保持原样，不承担后续同步维护。

## 待明确事项

以下均为未决问题，不是对已接受要求的改写。由项目所有者及相关接口消费者确认会影响可观察行为的定义后，同步相应规格；不能先以实现选择暗中确定语义。

| 事项 | 所属边界与影响 |
|---|---|
| 具体操作、HTTP 路径/方法、认证与 tenant 身份来源、成功响应和完整错误 schema；字段类型、时间格式及 null/缺省语义 | API 和 worker 传输契约尚不足以直接发布 SDK 或独立插件；审计请求同样需要认证和传输定义 |
| Idempotency-Key 的 ASCII 字符范围是否包含控制字符，24 小时恰到期及窗口外 key 重用规则，JSON 重复键或数值解析精度的处理 | API 输入合法性、规范化比较及窗口边界；保留已接受的键序、数组序与 1/1.0 规则 |
| 终态任务重复取消的响应，以及取消请求如何在领取/心跳等协议中交付 worker | API 取消幂等的响应契约与 worker 接收取消的接口 |
| 结果结构、相同结果的相等判定、可重试/不可重试失败的表示；已接受结果后重放原确认与 R15 的过期拒绝如何在边界相交 | Worker 独立兼容性，不能默定终态后 token 或过期后的重放行为 |
| `kind` 枚举字面值、actor_type 取值与身份含义、事件字段类型；format_version 和 next_sequence 的承载方式；空批次 next_sequence | 审计消费者可独立导入及生成准确 golden 文件；不增加未授权事件字段 |
| HTTP 框架、持久化、队列需求与部署方式；如何满足可恢复审计、幂等和重启恢复 | 技术方案未选定。先说明不变量与备选取舍，再由有权负责人决定，不预置任何产品依赖 |

不必为未决事项先创建空的决策记录。某项选择确需独立维护其接受过程或理由时，再建立相应记录。

## 执行顺序

1. 与三个接口的消费者澄清上述对外定义，完成可实施的 wire schema、错误和边界规则；更新各自规格。涉及实质取舍先取得确认。
2. 在不预设产品的前提下设计跨接口的持久化、并发提交和可恢复审计方案；明确 R31–R33 的故障边界。基础设施选择需另行决定。
3. 实现公共 API、worker 协议和审计导出，共享必要的任务状态、tenant 隔离和提交语义。按下表逐项补充实现位置及实际验收证据，不用代码存在代替通过验收。
4. 分别组织 API 消费方、两个外部 worker 提供方和审计消费者验收；补齐并发 API 验收、独立 conformance suite、格式 golden 检查。
5. 执行整体规格规定的跨边界并发、故障恢复和重启验收。只有实际证据支持所有相关要求后才能声明交付。
