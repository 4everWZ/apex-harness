# Relay 产品规格

本文件及下属技术规格接管项目所有者已接受的 R01–R36，定义尚待实现的当前契约。契约已接受不表示系统已实现或通过验收。

## 范围与契约边界

Relay 提供租户隔离的任务创建、查询、取消、worker 执行协议及审计导出。当前接受的版本为 API v1、worker protocol v1、audit format v1。

| 契约所有者 | 消费方与发布边界 | 所有的详细要求 |
|---|---|---|
| [公共任务 API v1](task-api.md) | 移动端、合作方 SDK 随公共 API 版本发布 | R01–R12 |
| [Worker protocol v1](worker-protocol.md) | 两个独立于服务器团队的 worker 提供方，分别执行协议兼容性验收 | R13–R22 |
| [Audit format v1](audit-format.md) | 独立更新周期的审计消费者 | R23–R30 |

各层负责维护自身接口、数据语义、边界与验收；影响多个消费者的变更必须协调相关契约。实现细节不能自行改变公开契约。

## 共享一致性与持久化

- **R31：** 状态已向调用方显示提交时，对应审计事件必须可恢复。事务或 outbox 的具体实现未决定；静默丢失审计不可接受。
- **R32：** API 层不得把 expired lease 当作成功结果；worker 层不得绕过 tenant 隔离；审计事件必须对应同一次已提交状态转换。
- **R33：** 服务重启后必须保留任务、幂等窗口和各 tenant 的审计顺序。这些承诺不得依赖进程内状态。
- **R34：** worker 内部算法和部署拓扑不属于当前公开契约。HTTP 框架、数据库、队列和部署方式均未选择；本规格不指定中间件或数据库产品。
- **R35：** 本轮不包含计费、管理 GUI、跨地域复制。
- **R36：** 开发跨多次会话。API 消费方、worker 提供方、审计消费方分别验收各自接口，之后执行跨边界一致性验收。当前没有任何实现符合性证据。

## 跨边界验收

| 要求 | 必须建立的证据 |
|---|---|
| R31 | 覆盖提交与故障交界：凡已向调用方显示提交的创建、开始、取消请求、终态转换，其对应审计事件在恢复后仍可取得；失败事务不伪造已提交事件。具体故障注入点随所选持久化方案定义。 |
| R32 | 联合 API、外部 worker 和审计消费者验证租户隔离、过期 attempt 的迟到结果、终态竞争；验证最终可见状态与审计确实来自同一次提交。 |
| R33 | 在存在任务、有效幂等窗口和审计分页历史时重启服务，验证任务状态、原创建响应重放及 tenant_sequence 顺序与历史重放语义保持。 |
| R34–R35 | 评审实现范围和对外依赖，确认公开契约及交付范围未被未经接受的基础设施选择或新增功能改写。 |
| R36 | 分别取得三类消费方验收及联合一致性验收结果；任何缺失的验收仍为未验证，不能仅凭文档或单层测试宣称交付。 |
