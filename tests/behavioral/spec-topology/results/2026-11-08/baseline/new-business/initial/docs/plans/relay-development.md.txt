# Relay 开发工作计划

- **Goal：** 实现已接受的 Relay 三类接口，分别完成消费方验收，再完成跨边界一致性验收，使工作可跨会话继续。
- **Primary contracts：** [Relay 产品规格](../specs/relay.md)。
- **当前状态：** 已建立维护规格；尚无应用实现，所有实现及符合性验收均未完成。当前任务只准备文档，未执行实验、部署或实现验证。

## 工作与要求映射

| 工作 | 对应要求 | 完成条件 | 当前状态 / 依赖 |
|---|---|---|---|
| 明确未定义的接口细节，取得项目所有者接受后更新相应技术规格 | R01–R30 | 请求、响应、错误与导出格式足够确定，双方实现无需猜测；不更改已接受语义 | 待办；见下方待决定事项 |
| 选择满足持久化和提交一致性的实现方案 | R31–R34 | 明确框架、存储、调度、事务/恢复边界，能实现现有契约；需要独立维护的重大选择另记决策 | 待办；当前不选择基础设施 |
| 实现公共任务 API v1，并由 API 消费方验收 | R01–R12 | 租户隔离、规范化幂等、状态和取消、查询分页实现；通过对应技术规格验收，包含并发竞争 | 未实现 / 未验证；依赖接口细节及持久化方案 |
| 实现 worker protocol v1，建立独立 conformance suite | R13–R22 | 服务器与两个外部 worker 提供方分别通过到期、重放、冲突、取消、次数耗尽验收 | 未实现 / 未验证；依赖协议 wire 定义与任务状态实现 |
| 实现 audit format v1，并由审计消费方验收 | R23–R30 | 事件记录、隔离与分页导出实现，golden 文件场景全部验收 | 未实现 / 未验证；依赖枚举、导出 wire 定义及提交方案 |
| 联合一致性及恢复验收 | R31–R33、R36 | 三类接口先各自通过验收；再验证同次提交、过期 lease、tenant 隔离、故障恢复与重启持久化 | 未验证；依赖上述实现与分层验收 |
| 确认交付范围并关闭本计划 | R34–R36 | 不含计费、管理 GUI、跨地域复制；符合性证据完整、规格与接受的变更同步 | 待办；交付前保持计划当前 |

下一会话从接口澄清开始。实现阶段将实际验证结果及其所在位置填入本计划；不把任务勾选或静态文档检查当作行为符合性证据。当前无需交接文档：尚未发生责任转移。

## 待决定事项

以下仅标识缺口，不是已接受的新行为。接受澄清后更新所属技术规格；若拟议答案改变现有要求，先由项目所有者决定。

| 范围 | 实现或验收前需明确的内容 |
|---|---|
| API 请求与响应 | 操作路径/方法、创建与取消响应及错误体、身份认证及 tenant 来源、允许类型注册/授权入口、字段类型和时间编码、查询参数与 cursor 约束；24 小时到期边界及窗口后 key 再使用语义。 |
| 请求比较与状态边界 | 规范化请求包含哪些字段；JSON 异常输入的处理；终态再次取消的具体响应；取消请求遇 lease 到期/可重试失败时如何继续；并发分页期间的一致性保证。 |
| Worker wire 语义 | 领取请求/无任务响应、心跳响应及取消标记传递、结果结构与相等判定、重试错误分类、取消确认消息、协议版本协商位置；完成后重放确认如何与 R15 的过期拒绝规则衔接。 |
| 审计 wire 语义 | kind 与 actor_type 的声明枚举、字段类型、事件与状态转换的精确对应；format_version 和 next_sequence 的传输位置；空批次 next_sequence；无重复状态转换时的取消重放是否产生新的取消请求事件。 |
| 基础设施与验证设施 | 框架、数据库、队列、部署方式均未决定；持久化/原子性方案、可控服务端时间、并发调度及故障恢复测试方法在后续设计阶段确定。不得以选型为由弱化已接受契约。 |

这些事项影响对应部分的实现或精确验收，当前文档准备可以完成；尚不能宣称接口 wire 定义齐备或任何实现通过验收。
