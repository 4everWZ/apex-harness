This routes to `governing-project-work` plus `shaping-solutions` in **Plan** mode. The API design is already approved, so `shaping-solutions` does not reopen the design gate unless a genuinely material unresolved choice is discovered.

`governing-project-work` owns the documentation obligation and source-of-truth decision: it determines that this substantial cross-service work needs a durable artifact, selects the repository's existing canonical plan location or (only if none exists) the neutral `docs/plans/` fallback, and ensures each decision has one owner. The approved spec or design record remains authoritative for API behavior and rationale; the plan should link to it rather than duplicate it. Any cross-cutting tradeoff that must persist belongs once in its designated decision or tradeoff record, with the plan linking to that record.

`shaping-solutions` consumes that governance boundary and owns the implementation plan's content and quality. It should produce ordered, dependent, independently testable tasks; identify affected files or component responsibilities and cross-service interfaces; cite source requirements and constraints; state observable acceptance and exact verification commands where known; include documentation impact and unresolved blockers; and include commit boundaries only if commits are authorized. Setup, configuration, and documentation work should be folded into the task whose deliverable requires them.

In short: governance decides **whether a durable plan is required, where it lives, and which artifact owns each fact**; shaping decides **what the selected plan says and whether it is execution-ready**. Neither skill should create a competing specification or restate the approved API design inside the plan.
