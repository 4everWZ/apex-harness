# Specification coverage comparison — 2026-11-01

Three current-rule baseline executions did not reproduce missing ordinary-development semantics. After a small coverage-guidance clarification, four fresh executions and semantic review found no substantive omission, unsupported accepted requirement or medium/high-risk contradiction. This is evidence of compatibility with the tested cases, not a causal fix or a measured reliability improvement.

## Change

The fallback specification template now prompts for users/use cases, operating conditions/dependencies, ordinary user flows, states, business rules, data, configuration, compatibility and applicable quality requirements. Its detail section is named `Contract details — as needed` and may be omitted when the preceding contract is sufficient. Necessary detail is not made optional, and a separate technical file is not required merely to fill a section.

One sentence in the existing drafting paragraph judges completeness by intended-use understanding, consistent implementation and assessable conformance without unstated assumptions; material gaps remain explicit. No workflow, required checklist, coverage matrix, metadata, template file or validator rule was added. The accepted-contract definition, exact technical semantics, ownership, layer selection, source handling, evidence boundary, retirement and recovery rules remain unchanged.

The [baseline template](2026-11-01/candidate-baseline/managing-project-docs/assets/templates/specification.md.txt) and [baseline lifecycle](2026-11-01/candidate-baseline/managing-project-docs/references/specifications.md.txt) are retained with other supplied candidate materials. The exact [revised template](2026-11-01/candidate-revised/managing-project-docs/assets/templates/specification.md.txt) and [revised lifecycle](2026-11-01/candidate-revised/managing-project-docs/references/specifications.md.txt) are captured separately; all other candidate resources matched baseline.

## Execution and review

Seven executors each started with no inherited conversation: three baseline contexts and four revised contexts. Only skill-creator was activated. Executors received their actual task, isolated project, candidate skill/references and applicable fallback template, without suspected weaknesses, proposed edits, expected answers, reviewer criteria, previous runs or other cases. They did not use installed skill copies. Writes were restricted to repository-local temporary projects, with no implementation execution, network, dependencies or commits.

A separate reviewer compared actual artifacts and raw accepted requirements in both phases. Review used [semantic criteria](../review.md), not heading, word-count, identifier or link-check scores. It traced user journeys, states, business rules, failures, configuration effects, compatibility, quality conditions and unresolved choices. The algorithm regression also checked mathematics, numeric boundaries, identity/state effects and recovery. Internal implementation choices could vary where the contract allowed them.

## Validation and limits

Official skill/package structural validation and diff-whitespace checks passed. Local report links, candidate correspondence and captured outputs were checked separately. These structural/integrity checks are not behavioral evaluation or implementation evidence.

Each case has one execution per listed phase. Baseline already met the semantic criteria, so optional-section wording was not demonstrated to cause omission and the revision cannot be called a reproduced defect fix. The results do not establish long-context reliability, optimal document length or universal completeness. They show that the clarified prompts supported complete ordinary-business, small-tool and detailed-algorithm documents in these cases without observed regression.

No implementation, product acceptance, runtime integration or performance measurements were performed. Lifecycle instructions were unchanged; this round did not rerun handoff, cancellation or recovery scenarios. Repository source is updated; no installation synchronization, commit or push was performed. Reusable cases and comparison evidence are retained, and only the current run's disposable workspace was cleaned.
