In the supplied APEX baseline, these are not documented as migrated aliases in a seven-skill series. They are still first-class leaf-skill names, so `using-apex` handles the request literally and in the user-specified order:

1. Route to `brainstorming` if material intent or design choices remain. It clarifies the design and blocks implementation until the user approves the material direction. If there is no unresolved design decision, its trigger is absent and APEX should not manufacture a brainstorming phase.
2. Then consider `subagent-driven-development` for implementation. The name alone does not authorize delegation. That leaf can run only for an approved, bounded plan when APEX has selected delegated, independently reviewed, commit-based execution; the required roles and edit/commit authority must exist, `HEAD` must resolve, and the Git workspace/index must be clean. If those preconditions are absent, APEX stops using that leaf and chooses the smallest applicable mechanism, normally inline execution through `executing-plans`, or reports the missing boundary.

Thus an explicit request makes APEX consider both named leaves, but it does not override their triggers, approval gate, governance, authority, or repository-state checks. The baseline provides no evidence for translating these old names to new seven-skill names, so inventing a migration mapping would be incorrect.
