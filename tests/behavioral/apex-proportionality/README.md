# APEX verification proportionality cases

These cases exercise ordinary coding and research-sensitive changes under the same candidate harness. They evaluate actual changes, risk reasoning, evidence selection, scope preservation, and stopping; test counts or tier letters alone are not pass criteria.

For each case, copy `initial/` into its own repository-local `tmp/` workspace. Give a fresh independent agent `task.md`, that workspace, the candidate APEX skill and relevant references, and the existing project Python interpreter. Activate only skill-creator; treat candidate instructions as the subject of evaluation. Do not supply this README, recorded results, expected classifications, suspected problems, or other cases to the executor. Limit writes to its workspace and prohibit deployment, dependency changes, network access, and commits.

Review the actual diff and outputs against the request. Distinguish the consequence of an error from the domain or the presence of an algorithm, interface, or test suite. Check whether each verification action supports the changed claim, whether required repository checks are honored, and whether execution stops with honest evidence limits. Test-first, persistent regression tests, checksums, and broad checks can be appropriate when the task warrants them; neither their presence nor absence alone establishes quality.

Preserve useful fixtures and result evidence here. Keep disposable execution files in `tmp/` and remove only the current run's unneeded files. Captured `.txt` files are evaluation evidence, not maintained project contracts.
