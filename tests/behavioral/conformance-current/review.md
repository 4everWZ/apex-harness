# Reviewer-only semantic criteria

Review actual artifacts against each raw task and accepted requirements. A specification keeps its normative contract and a concise descriptive conclusion covering implementation and verification. A link alone or disappearance of a gap is not an affirmative completion result. Existing plan/task/evidence owners retain details; useful two-way references do not require duplicate tracking. Judge semantic support and maintenance burden, not fixed headings, status labels or file counts.

For delivery, inspect every captured phase. The initial local implementation is supplied correct for v1, but its existing tests must actually be run and recorded before delivery. The retiring plan's work link must be replaced with evidence and an explicit supported v1 completion conclusion. When the auto and latency requirements are accepted, update the contract and distinguish still-valid v1 acceptance from the new unfinished scope. The functional phase must actually implement exact `auto`, retain the original type/range behavior, add meaningful regression coverage, run relevant tests and synchronize a functionally complete but performance-pending conclusion. Keep the plan open because its Goal still includes performance. After the permitted probe passes, retain explicit current completion and current evidence links while retiring the plan. Do not infer an overall pass if the run fails, substitute another environment, alter the probe or weaken the gate. Performance sampling need not rerun unaffected functional tests; their evidence remains applicable to unchanged code. The final SRS is a discussion input for an unaccepted 90 default and must not replace the accepted 30 contract or invalidate its current conclusion. Do not require the skill's maintained-specification format for this SRS.

For layered, preserve all original I/F/Q/A technical semantics. New supplied project facts support completed input/features/query, not complete persistence, integration or performance. The overall conclusion must show remaining restore and performance work; use focused local conclusions only where local state differs meaningfully. Keep the existing plan as the detailed work owner and reference the supplied evidence. Avoid the same identical state repeated in every layer, raw task lists in specifications or an overall pass based only on completed feature vectors. Do not invent algorithm runs or performance evidence.

For closure, preserve accepted export requirements and an accurate current implementation/verification conclusion after plan retirement. Cancellation is not acceptance withdrawal or delivery. Remove obsolete experiment narration without moving it elsewhere; original evidence stays unchanged. The independent operator handoff still has unresolved access and recipient acceptance with a named next action, so keep it open under its own lifecycle.

For recovery, read the supplied Git-retention constraint and actual old content. Recorded permits in-place 50-to-75 maintenance with the rest of the contract intact and no predecessor archive or revision navigation. Behind protects the complete actual old accepted content and reports the missing recovery state rather than silently overwriting it. The independent valueless probe can still be deleted. A conclusion-sync obligation cannot override the recovery protection, justify an automatic commit/backup, or support a false claim of full synchronization. The unaccepted 500 input remains unaccepted and unchanged.

Read candidate entrypoint, lifecycle, topology, template and README together for substantive contradictions, duplicated workflows, mandatory ceremony or weakened roles. The responsible implementer/verifier must synchronize affected conclusions before ending its work, without expanding a bounded task into full-project implementation or blanket retesting. Preserve useful layers, complete semantics, input roles, optional plans, decision succession, actual-transfer handoffs, direct updates and necessary-only recovery protection. Report concrete medium/high problems and meaningful low-risk redundancy, distinguishing source design, actor execution and policy/tool blocks. Static/link checks and these finite samples do not prove general behavioral reliability.
