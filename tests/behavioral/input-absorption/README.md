# Input absorption and source ownership cases

These cases evaluate how supplied requirements become maintained project information without automatically becoming another retained source document. Actual document responsibilities, accepted semantics, unresolved work and original-source handling matter; a directory name, file count, wording, or source-integrity check alone is not a behavioral pass criterion.

Copy each case's `initial/` to its own repository-local `tmp/` workspace. Give a fresh independent executor only its `task.md`, its project, skill-creator, and the candidate skill/reference material. Activate only skill-creator. Do not supply reviewer criteria, proposals, expected answers, suspected problems, historical examples, reports or other cases. Restrict writes to the isolated project and prohibit network, dependencies, implementation execution and commits.

For new and existing projects, capture initial artifacts before giving `later-task.md` to the same executor. Review the continued project as well as the initial outcome. The explicit-retention, versioned-source and mixed-materials cases each have one task. They cover a user-requested immutable customer record, an external review that needs the complete original, and product requirements supplied alongside non-product submission/review instructions.

Review all newly created and changed files, not only the original input. Check whether any additional original-text copy, relocated source or embedded original has a task-established role. Reusing accepted requirement wording in its proper specification is not itself unwanted duplication. Verify full required semantics, separation of unaccepted targets, existing canonical ownership, unfinished-plan state, and whether evidence limits remain honest. Do not infer conformance from requirement-ID counts or passing link checks.

Candidate and generated document captures use `.txt` as evaluation evidence; they are not maintained project documents. Preserve useful cases and comparison evidence here. Keep disposable execution material under repository-local `tmp/` and remove only the current run's unneeded files.

The applied cases additionally cover a substantial new-project SRS, an existing maintained specification, and input already written in the specification shape. They reuse the existing mixed-material and useful-original cases; document ownership, completeness and unnecessary duplication are reviewed semantically.

The authored SRS case starts during project maintenance: the user requests either a [traditional SRS](cases/authored-srs/task.md) or simply an [SRS](cases/authored-srs/task-plain.md) in `tmp/` for a requirements discussion. Run each wording in its own fresh context. Capture that output and all project files before delivering its [later task](cases/authored-srs/later-task.md) to the same executor. Only then does the user accept selected changes and request development preparation. Give executors neither the later task early nor the [review criteria](cases/authored-srs/review.md). The [2026-11-01 executions](results/2026-11-01-srs-intent.md) cover both wordings and a fresh new-project import: the requested SRS formats and contract absorption worked, but one follow-up unnecessarily annotated the temporary SRS. The report records that deviation rather than treating every stage as passed.
