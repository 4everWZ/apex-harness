# Relay 产品契约

本文件维护 Relay 已接受的产品范围、跨接口不变量和整体验收要求。项目所有者已接受的 [需求输入](../../tmp/product-srs.md) 是建立本契约的基线，不承担后续维护职责，也不随项目文档同步修改。需求编号 R01–R36 保留用于定位；契约接受不表示实现已完成或符合性已验证。

## 契约边界

Relay 包含以下分别维护、发布和验收的契约。各文档拥有对应接口的规范内容，不能以其中一个接口的实现或测试替代另一个接口的验收。

| 当前接受版本 | 规范所有者 | 独立消费者与验收边界 |
|---|---|---|
| 公共 API v1 | [公共任务 API](relay-api-v1.md) | 移动端和合作方 SDK 按公共 API 版本发布 |
| worker protocol v1 | [Worker 插件协议](relay-worker-v1.md) | 两个不隶属服务器团队的提供方按插件协议开发，独立验收兼容性 |
| audit format v1 | [审计导出格式](relay-audit-v1.md) | 审计消费者按格式导入，更新周期不依赖 API 发布 |

内部算法、开发阶段和实现模块不单独构成公开契约。各接口的变化应在其所属规范中维护；影响以下共同承诺的变化还必须同步本文件。

## 跨边界一致性与持久性

- **R31**：状态向调用方显示为已提交时，对应审计事件必须可恢复。具体事务或 outbox 实现未决定；静默丢失审计事件的设计不满足契约。
- **R32**：API 层不能把过期 lease 当作成功结果；worker 层不能绕过 tenant 隔离；审计记录必须对应同一次已提交状态转换。
- **R33**：服务重启后必须保留任务、幂等窗口和审计顺序。这些承诺不能依赖进程内状态。

## 范围

- **R34**：worker 内部算法和部署拓扑不是当前公开契约。HTTP 框架、数据库、队列和部署方式尚未决定；任何消息中间件或数据库产品均不是已接受的依赖要求。
- **R35**：本轮不包含计费、管理 GUI 或跨地域复制。
- **R36**：开发跨数次会话完成。API 消费方、worker 提供方和审计消费方分别验收其接口，再执行跨边界一致性验收。

## 整体验收

各接口须先通过其规范中的独立验收。随后组合验证 R31–R33：状态提交与审计恢复对应、过期或旧 attempt 的结果不能变为成功、worker 访问不破坏 tenant 隔离，以及服务重启不丢失任务、幂等窗口或 tenant 内审计顺序。验收必须能区分未提交操作与已提交操作，不能只以正常返回示例推断这些保证成立。

本文规定应达到的行为；实现进度、尚缺的接口细化和实际验收证据由当前工作计划维护。
